We moved our job queue from Redis to Postgres

For the last six months, our background jobs have lived in a small Redis cluster. It worked well. It also meant a second persistence system to monitor, back up, and explain to new teammates.

Last week we moved the queue into Postgres. The change is deliberately unexciting: jobs are rows, workers claim them with SKIP LOCKED, and retries use a timestamp column with a partial index.

What changed for us

  • One fewer service in the deployment.
  • Job history can be inspected with the same tools as the rest of the product.
  • At our current volume, the database has plenty of headroom.

The migration took a day, including a week of dual writes in staging. We did not see a meaningful change in median latency, and the p99 is still comfortably inside our budget.

sql · claim next jobCopy
UPDATE jobs
SET claimed_at = now(), attempts = attempts + 1
WHERE id = (
  SELECT id FROM jobs
  WHERE run_at <= now() AND claimed_at IS NULL
  ORDER BY run_at
  FOR UPDATE SKIP LOCKED LIMIT 1
)
RETURNING *;

This is not a universal recommendation. If your queue is doing millions of writes per second, use the tool built for that. For a small product team, fewer moving parts turned out to be the better trade.

Curious what queue shapes other teams have found comfortable at this scale.
